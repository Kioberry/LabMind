## 0. 一句话结论

**在一个我们自己设计的, 已知最优点的模拟目标函数上 (in simulation), LabMind 的选点策略在 5 批 x 20 个实验后, 离最优点的差距 (simple regret) 平均是 0.132, 随机采样是 0.340, 低了约 61%; 30 个种子里 83% 的种子 LabMind 更好 (Wilcoxon p ≈ 1.2e-5). 但这只证明了 "在模拟里, 这个采样策略比随机好", 不能证明它在真实湿实验里提高了转染率. 真实 Claude agent 的决策耗时这次没测到, 因为代码里写死的模型 `claude-sonnet-4-20250514` 已经返回 404.**

## 1. 为什么要做这件事: 原来的 "31%" 为什么站不住

先把因果链摆出来, 这是整件事的起点.

**1) 转染率和参数根本没关系.** 看 `backend/image_processing.py` 的 `process_experiment(well_index, exp_id, batch_id)`:

- 它按 **孔的编号** (第 1 个实验读第 1 个孔, 第 2 个读第 2 个孔...) 去读 BBBC016 的 TIF 图, 然后数细胞核和 GFP 阳性细胞.
- 再加一点按 (批次, 实验 id) 生成的随机噪声 (sd 0.025).
- 它 **从来没看过** 这个实验的 pH, 温度, 浓度, 脂质比, 孵育时间.

所以不管优化器提什么参数, 第 i 个实验拿到的分数都差不多是 "第 i 个孔的图 + 噪声". 优化器不可能让结果变好, 就像你改考试答案, 但老师只按你座位号打分.

**2) 已有数据也证明了这一点.** B1 最好 0.202, 平均 0.092; B2 最好 0.168, 平均 0.092. B2 是 LabMind 根据 B1 "优化" 出来的, 平均值一点没变, 最好值反而低了. 这正是 "分数和参数无关" 时会看到的样子.

**3) 所以 "提高成功率 31%" 没有任何数据来源.** 仓库里找不到哪个计算能得出 31%. 面试官只要问一句 "31% 是怎么算的, 和什么比的", 就答不上来.

**4) "决策时间从几小时降到 1 分钟以内" 也站不住.** README 里的 "几小时" 指的是做一批湿实验要几小时 (实验本身的时长), 不是 "科学家看数据, 决定下一批做什么" 的时间. 拿实验时长去和 agent 的计算时长比, 是偷换概念. 而且这次实测: 光是图像处理一批就要 86 秒, 已经超过 1 分钟, 还没算 Claude 的调用时间.

**那怎么办?** 真实的湿实验我们做不了. 但我们可以回答一个更小, 但诚实的问题: **"如果分数真的取决于参数, LabMind 的选点策略能不能比瞎选更快找到好参数?"** 这就需要一个 "已知答案" 的考场, 也就是模拟目标函数. 下面每一步都是为了把这个问题回答得可信.

## 2. 每一步做了什么, 为什么这样设计

所有提交都在 `main` 分支本地, 没有 push. 按顺序:

| commit | 内容 |
|---|---|
| `218ec5a` | 重构: 把选点逻辑抽成纯函数 `propose_candidates` |
| `dd8df4b` | 模拟目标函数 `simulation.py`, 用 `OBJECTIVE_MODE` 切换 |
| `791bbab` | 随机基线 `baselines.py` |
| `63fee0e` | 离线评估脚本 `evaluate.py` |
| `4535dc9` | 计时埋点 + `benchmark_timing.py` |
| `5cd6214` | pytest 测试 (20 个) |
| `a6e75a2` | 跑出来的原始结果 `docs/eval/*.json` |
| (本文档所在的 commit) | 这份讲义 |

### 第 0 步 (`218ec5a`): 先把 "被测对象" 拆出来

原来的 `generate_next_batch_impl` 一个函数干了三件事: 采样, (可选) 调 Claude 改约束, 写文件. 评估时我们只想测 "采样策略本身", 不想每次都调 LLM, 也不想往 `data/` 里写文件.

所以把采样那一段原封不动搬进 `propose_candidates(top_performer, batch_id, seed=None)`. **重点: 行为不能变.** 我用旧版本和新版本对同一个输入各跑一次, 20 个候选逐字节相同, 才提交. 这叫 "先重构, 再加功能", 两件事分开提交, 出了问题好定位.

为什么要加 `seed` 参数? 线上代码的随机种子是从批次名算的 (`sum(ord(c))`), 也就是说每次跑 "B2" 都用同一个 LHS 设计. 评估要跑 30 个不同的种子, 所以需要能从外面传种子. 不传时行为和以前完全一样.

### 第 1 步 (`dd8df4b`): 模拟目标函数, 一个 "已知答案的考场"

文件: `backend/simulation.py`. 它是一个 **人为设计的** 响应曲面, 不是生物学:

- 一个主峰 (全局最优): pH 7.4, 37 °C, 0.30 mg/mL, 脂质比 3:1, 孵育 5 小时, 峰高 0.80.
- 一个次峰 (诱饵, 局部最优): pH 6.4, 40 °C, 0.15 mg/mL, 4:1, 3 小时, 峰高 0.45.
- 一个底噪 0.03, 再加测量噪声 (默认 sd 0.03, 和原图像路径的 0.025 差不多).
- 最优值 f* = 0.830. 随机撒点的平均真实值约 0.07, 和真实 B1/B2 的平均 0.092 在一个量级.

为什么这样设计:

- **为什么要 "已知最优"?** 只有知道满分是多少, 才能算 "离满分还差多少" (regret). 真实实验永远不知道满分.
- **为什么要平滑的高斯峰?** 真实的配方响应一般是平滑的: pH 从 7.3 变到 7.4, 效果不会突然跳变. 太离谱的曲面 (比如完全随机) 任何方法都学不到东西, 没有意义.
- **为什么要一个诱饵次峰?** LabMind 是 "围绕当前最好点附近找" 的局部搜索. 如果曲面只有一个峰, 局部搜索就太占便宜了. 加一个次峰, 才能看到它会不会被困住.
- **为什么最优点放在整数温度, 整数小时, 3:1 上?** 因为 LabMind 提的参数会被取整 (温度和小时取整数, 脂质比只能是 2:1/3:1/4:1). 如果最优点在 37.5 °C, 谁都到不了, regret 永远不为 0, 不公平.
- **为什么叫 "可插拔"?** 设 `OBJECTIVE_MODE=simulation`, 应用里每个实验的分数就来自这个函数 (用这个实验自己的参数算), 处理日志里会标 `[simulated objective]`. 不设或设成 `image`, 一切和原来一样. 图像照样会渲染出来, 前端的对比图不会坏.

**这一步最容易被挑战的地方:** 曲面是我拍脑袋定的. 峰的位置, 宽度, 诱饵高度都会影响结论. 所以文档里每个数字都要带 "in simulation".

### 第 2 步 (`791bbab`): 随机基线, 没有对照就没有结论

文件: `backend/baselines.py`, 函数 `random_lhs_batch`. 每一批都在 **整个参数空间** 里重新撒 20 个 LHS 点, 完全不看之前的结果.

为什么需要它? "LabMind 5 批后 best 到 0.709" 这句话本身没有意义. 0.709 是好是坏? 要和一个最笨但合理的方法比. 随机采样就是这个 "最笨但合理": 预算一样 (每批 20 个), 取整规则一样, 唯一区别是 "用不用历史结果". 这样差别只能归因于 "用了历史结果".

为什么是 LHS 而不是纯 `uniform`? 因为 LabMind 自己也用 LHS. 两边用同一种撒点方式, 比较的才是 "往哪撒", 不是 "怎么撒".

### 第 3 步 (`63fee0e`): 离线评估脚本, 多种子, regret

文件: `backend/evaluate.py`. **它不调用 Claude.** 在应用里, Claude 负责决定调用 `generate_next_batch` 工具, 但候选参数本身完全由 `propose_candidates` 算出来, Claude 不改数字 (除非研究员加约束). 所以评估直接调用 `propose_candidates`, 测的是 "采样策略", 不是 "Claude 会不会正确调用工具".

每个种子的流程:

1. B1: 一个全空间随机 LHS 批, **两种方法共用** (同一种子, 同一起点, 这样比较是配对的, 方差更小).
2. B2 到 B5: LabMind 找 **上一批** 观测值最高的实验, 在它周围 ±25% 范围里撒 20 个点. 这完全照搬 agent 的行为 (agent 只看刚做完的那一批, 不看全部历史). 随机基线则重新全空间撒点.
3. 每个点用模拟函数打分 (带噪声).

指标:

- **best-so-far**: 到这一批为止, 做过的所有实验里, 真实值 (无噪声) 最高的是多少. 只会上升.
- **simple regret**: f* 减去 "推荐点" 的真实值. 推荐点 = 到目前为止 **观测值** 最高的那个实验, 也就是科学家真会拿去用的那个配方. 为什么用观测值挑, 用真实值评? 因为现实里你只能看到带噪声的观测, 可能挑错 ("赢家诅咒"), regret 要把这个代价算进去.
- **batches-to-threshold**: 第几批第一次达到 90% 的 f*. 没达到就记 "没达到", 另外报告达到的比例.
- **均值, 标准差, 95% 置信区间**: 用 t 分布, 30 个种子.
- **配对检验**: 同一种子两种方法的最终 regret 相减, 看差的置信区间和 Wilcoxon 符号秩检验.

为什么要多种子? 只跑一次, 结果可能是运气. 第 3 节的表里你能看到, LabMind 最终 regret 的标准差是 0.166, 比均值 0.132 还大. 单跑一次可能拿到 0.0 也可能拿到 0.6, 随便挑一个写进简历就是 cherry-picking. 30 个种子 + 置信区间才能说 "平均来看, 有多确定".

### 第 4 步 (`4535dc9`): 计时, 让 "决策时间" 变成一个真实数字

两部分:

- **应用内埋点** (`main.py`, `tools.py`): 每一批记录 "测量计算时间" (不含每个实验 0.4 s 的演示 sleep) 和 "agent 决策时间" (整个 Claude 工具调用循环), 写到 `labmind.timing` 日志和 `state.json` 的 `timings` 字段, 处理日志里也会显示一行.
- **独立基准脚本** (`benchmark_timing.py`): 不用启动前端, 直接测: 真实图像处理 20 个孔, `propose_candidates`, 以及 (加 `--with-agent` 且有 API key 时) 真实 Claude 循环. agent 那一步在临时目录里的数据副本上跑, 不动真实状态.

为什么要排除 sleep? 那 0.4 s 是为了前端日志一行行出现的效果, 不是计算. 算进去就夸大了耗时; 反过来如果拿 "去掉 sleep" 的数字说 "我优化了速度", 也是作弊. 要说清楚测的是什么.

**这次实测的诚实结论:** 图像处理一批 86 秒, 选点 0.18 毫秒. 完整 agent 循环没测到: Anthropic API 对 `claude-sonnet-4-20250514` 返回 404 (这个模型已下线). 这也意味着 **线上的 agent 现在应该是跑不通的**, 需要换一个当前可用的模型 id (这次没改, 因为改模型会改变产品行为, 应该你自己决定). 换完以后再跑 `python benchmark_timing.py --with-agent`, 就有真实的 "决策时间" 了.

### 第 5 步 (`5cd6214`): 测试

`backend/tests/` 下 20 个 pytest 测试, 全部通过. 测的是 "评估本身可不可信":

- 最优点真的是全局最优 (随机撒 2 万个点都不超过它), 而且在网格上可达.
- 噪声无偏 (4000 次测量均值约等于真实值).
- LabMind 的候选确实在最好点附近, 随机基线确实覆盖全空间.
- 两种方法在 B1 结果相同; 没噪声时 regret = f* - best-so-far; 置信区间公式和手算一致.
- 模拟模式下 `main.py` 的打分来自参数, 计时会写进状态.

为什么要测评估代码? 因为评估代码有 bug, 得出的数字会比没有数字更糟糕: 它看起来很科学, 但是是错的.

## 3. 结果怎么读 (包括不好看的部分)

- **LabMind 明显好于随机.** 第 2 批就拉开差距, 之后一直保持. 配对差的置信区间 [0.134, 0.282] 不包含 0, p 值很小.
- **但它经常卡住.** 40% 的种子 5 批内没到 90%. 看最终 best-so-far 的分布: 有 3 个种子停在 0.2 到 0.44, 原因是 B1 的最好点离主峰太远, 局部搜索只在附近转. 还有不少种子停在 0.62 到 0.72: 搜索框永远是全范围的 ±25%, 不会缩小, 加上取整, 很难精细逼近峰顶.
- **噪声几乎不影响结论.** 0, 0.03, 0.06 三档结果的置信区间互相重叠. 噪声 0 时 LabMind 反而略差一点, 在区间内, 属于随机波动, 不要过度解读.
- **LabMind 不是贝叶斯优化.** 系统提示词和工具描述都说 "Bayesian optimization", 但代码里没有代理模型 (比如高斯过程), 也没有采集函数 (比如 EI). 它实际是 "围绕当前最好点的局部 LHS 搜索", 更像 trust-region 或爬山. 简历和面试里请用准确的名字.

## 4. 简历怎么写: 诚实的写法 vs 越界的写法

原则: **每个数字要能说出 "和谁比, 在什么条件下, 跑了几次".** 涉及优化效果的数字必须带 "in simulation".

可以写 (都有数据支撑):

- "Built an offline evaluation harness (30 seeds, 5 batches x 20) on a simulated response surface with a known optimum; LabMind's local LHS sampler cut final simple regret by 61% vs. a random LHS baseline (0.13 vs. 0.34, paired Wilcoxon p < 0.001), in simulation."
- "In simulation, reached 90% of the known optimum within 5 batches in 60% of seeds vs. 3% for random sampling."
- "Instrumented per-batch timing: image analysis of a 20-well batch takes about 86 s, candidate generation under 1 ms."
- "Found the original image-based scoring was independent of the proposed parameters, and replaced claims with a reproducible, tested evaluation (20 pytest tests)."

越界, 不要写:

- "Improved transfection success rate by X%". 没有任何真实湿实验数据支持, 模拟不是转染率.
- 去掉 "in simulation" 的任何优化数字.
- "Reduced decision time from hours to under 1 minute". 一是 "hours" 是实验时长不是决策时长; 二是完整 agent 时间没测到; 三是光图像处理就 86 s.
- "Bayesian optimization". 代码里没有代理模型, 叫 "Latin Hypercube local search" 更准确. 如果以后真加了高斯过程, 再改回来.
- "LabMind beats random by 44%" 这种只挑最好看的一个比率, 却不说是 best-so-far 还是 regret, 也不说区间. 要说就说清楚是哪个指标.

## 5. 面试会怎么追问, 怎么答

**Q: 61% 是怎么来的?**
A: 30 个种子, 每个种子 5 批 x 20 个实验. 第 5 批后 simple regret, 也就是最优值减去推荐配方的真实值, LabMind 平均 0.132, 随机 LHS 平均 0.340, (0.340 - 0.132) / 0.340 ≈ 61%. 是在模拟目标函数上测的, 不是湿实验.

**Q: 模拟函数是你自己定的, 那不就是你想要什么结果就有什么结果?**
A: 对, 这是这个评估最大的局限, 我会主动说. 我做了三件事降低这个风险: 一是曲面平滑, 量级和真实数据接近 (随机平均 0.07, 真实 B1 平均 0.09); 二是故意放了一个诱饵次峰, 专门惩罚局部搜索; 三是在三档噪声下重跑, 结论不变. 但它只能说明 "如果响应曲面大致长这样, 这个策略比随机好". 要证明真实效果, 需要真实实验或者用历史数据拟合的代理模型.

**Q: 为什么不直接用真实的图像数据评估?**
A: 因为现在的图像打分是按孔的编号读图加噪声, 和提出的参数无关. B1 平均 0.092, B2 平均 0.092, 就是这个原因. 在这种数据上, 任何优化器都不可能显示出效果, 评估没有意义.

**Q: 为什么要用观测值选推荐点, 却用真实值算 regret?**
A: 现实中只能看到带噪声的观测, 你会按观测挑配方. 用真实值评分, 才能把 "因为噪声挑错了" 的损失算进去. 如果用观测值算, 噪声大的时候会虚高.

**Q: 为什么 30 个种子? 为什么报告置信区间?**
A: 单次运行方差很大, LabMind 最终 regret 的标准差 0.166 比均值还大. 只报一次结果可能是运气. 30 个种子下, 均值的 95% 区间是 [0.070, 0.194], 和随机的 [0.296, 0.384] 不重叠, 配对检验 p ≈ 1e-5, 所以可以说差异是稳定的.

**Q: 你说是贝叶斯优化?**
A: 原来的描述是这么写的, 但我检查代码后发现没有代理模型和采集函数, 实际是围绕当前最好点的局部拉丁超立方搜索. 所以我在简历里改成了准确的说法. 如果要做真正的 BO, 下一步是用高斯过程拟合历史所有数据, 用 EI 选点, 再用同一个评估脚本和现在的方法比.

**Q: 它的缺点是什么? 你怎么改进?**
A: 40% 种子没到 90%. 两个原因: 只看上一批的最好点, 而不是全部历史; 搜索框固定 ±25% 不收缩. 改进方向: 用全历史最优做中心; 加 trust-region 式的收缩和扩张; 一部分预算留给全局探索; 或者上真正的 BO. 每个改动都能直接用 `evaluate.py` 比较.

**Q: 决策时间是多少?**
A: 分开说. 选点 0.18 ms, 可以忽略. 图像处理一批 20 个孔约 86 s (M2 Pro, Rosetta 下的 x86 Python). 完整 Claude 循环这次没测到, 因为代码里的模型 id 已经下线, API 返回 404. 埋点已经加好, 换模型后跑一次就有数.

**Q: 你怎么保证评估代码本身没 bug?**
A: 20 个 pytest 测试. 比如: 验证最优点真的是全局最优; 没噪声时 regret 等于 f* 减 best-so-far; 两种方法第一批结果完全相同; 置信区间和手算一致. 还有, 重构时我先确认新旧代码对同一输入输出逐字节相同, 再提交.

<summary>参考答案 (点开)</summary>

1. simple regret = f* - f(推荐点), 也就是 "推荐的配方离满分还差多少". 不知道 f* 就没法算 "差多少", 只能比相对大小, 所以必须用已知最优的模拟函数.

2. best-so-far 是 "做过的所有实验里真实值最高的", 历史只会增加, 所以只升不降. regret 看的是 "按观测值挑出来的推荐点". 新一批里可能出现一个观测值因噪声偏高, 但真实值更低的点, 它成为新的推荐点, regret 就会变大. 这就是赢家诅咒.

3. 因为 `process_experiment` 按孔编号读图再加噪声, 不读实验参数. 第 i 个实验的分数只取决于第 i 个孔的图, 所以不管提什么参数, 批平均都差不多. 根本原因在 `backend/image_processing.py` 的 `process_experiment`.

4. 为了只保留一个差别: 是否利用历史结果. 预算, 撒点方式, 取整都一样, 差异才能归因于策略. 如果随机每批 40 个, 预算翻倍, 比较就不公平了, 要么给 LabMind 也 40 个, 要么按 "总实验数" 对齐来比.

5. 起点一样, 两种方法的差别就不会被 "某个种子 B1 运气好" 干扰. 可以对每个种子做差, 用配对检验 (Wilcoxon), 方差比两组独立比较小, 更容易检测出真实差异.

6. 意思是: 如果重复整个 "跑 30 个种子求均值" 的过程很多次, 约 95% 次算出的区间会包含真实的平均 regret. 它描述的是 **均值** 的不确定性, 不是单个种子的分布. 单个种子的波动大得多 (标准差 0.166).

7. 次峰是诱饵, 让局部搜索有可能被困住, 更接近真实情况, 也让比较不至于偏袒 LabMind. 去掉后, 预计 LabMind 被困住的情况减少, 差距会变大. 这正是为什么要说明曲面是怎么设计的: 设计会影响结论.

8. sleep 是给前端日志做动画的, 不是计算. 算进去会夸大耗时. "不到 1 毫秒" 只是 `propose_candidates` 的耗时, 不包括图像处理 (约 86 s) 和 Claude 调用 (未测到). 把一个子步骤当成整个决策时间, 是以偏概全.

9. 代码里没有代理模型, 也没有采集函数. 它只是围绕上一批最好点在固定范围里 LHS 撒点. 真正的 BO 至少需要: (1) 一个用全部历史数据拟合的代理模型, 例如高斯过程, 能给出预测均值和不确定性; (2) 一个采集函数, 例如 Expected Improvement 或 UCB, 用来权衡探索和利用, 决定下一批点.

10. 第一句说的是真实转染率提高, 但没有任何真实实验支持, 而且 61% 根本不是转染率的变化. 第二句准确说明了指标 (simple regret), 对照 (random LHS), 条件 (in simulation), 每个词都能用仓库里的脚本和数据复现.

11. 这题没有标准数字, 要你自己跑. 思路: 半径越小, 越 "利用", 前几批提升快, 但更容易被困在诱饵峰或卡在 B1 附近, 达到 90% 的比例可能下降. 半径越大, 越接近随机, 不容易被困, 但逼近峰顶更慢. 好的回答要报告具体数字和置信区间, 说出这是探索和利用的权衡, 并指出可以让半径随批次收缩 (trust region). 注意: 你根据评估结果调参数, 再用同一个评估去报告效果, 会高估效果. 严谨的做法是换一批没用过的种子再测一次 (比如在 Python 里调用 `evaluate.evaluate(seed_offset=100)`).
